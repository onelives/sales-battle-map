01项目概述

项目名称：全湖北赛道智能销售工作台（仓库内代号 sales-battle-map）。

项目定位：面向 B 端 AI / 科技赛道销售的一体化客户管理、线索获客、智能分析个人工作台。以"作战地图 + 足迹点亮 + 双维获客 + 价值分析"为核心交互形态。

覆盖赛道：51 条 AI、数字化、智能硬件、企业服务、内容文娱、医疗科技全品类商业赛道（完整清单见 §4 数据字典）。

地域范围：仅限湖北省全域 17 地市州——武汉、黄石、十堰、宜昌、襄阳、鄂州、荆门、孝感、荆州、黄冈、咸宁、随州、恩施州、仙桃、潜江、天门、神农架。

存储方案：Neon Serverless PostgreSQL（替代 Supabase）。选择原因：Neon 提供零依赖 HTTP SQL 协议，后端无需驱动包即可读写，适配零依赖中转服务与 Serverless 部署。

数据源优先级：探迹开放 API（核心线索来源）→ 天眼查 / 爱企查（企业信息与动态补充）。

系统架构：前端页面 + 后端中转服务（密钥托管）+ Neon 数据库三层结构；所有第三方接口均走后端代理，禁止前端直接调用。

交付资产

  • 代码仓库：github.com/onelives/sales-battle-map（公开）
  • 正式链接：onelives.github.io/sales-battle-map/
  • 镜像链接：9lp22ycy.qwenwork.host（QW Pages）
  • 后端交付包：探迹Neon后端.zip / server/
  • Neon 项目：flat-lab-91250958

运行模式

  • 在线（真实）模式：部署 server/ 后前端自动探测 /api/health 切换，数据落 Neon。
  • 模拟模式：无后端时前端本地运行，线索/回填/账户均为模拟并明确标注；演示账户 admin / admin123。

03技术架构交接说明

三层架构与请求边界

前端静态页（GitHub Pages / QW Pages）
   │  仅调用同源 /api/*（Bearer Token）
   ▼
后端中转服务 server/（Node ≥18，零依赖内置模块）
   │  密钥托管 · 第三方代理 · 鉴权 · 批量写入
   ├─▶ 探迹开放平台（TUNJIE_APP_KEY/SECRET，仅环境变量）
   ├─▶ 天眼查 / 爱企查（动态补全，仅环境变量）
   └─▶ Neon Serverless PostgreSQL（DATABASE_URL / neon-config.js）

仓库结构

路径职责
index.html前端单文件应用（地图 / 看板 / 表单 / 登录权限 / 导出），全部库本地 vendor
data.js前端配置 + 本地示例数据（地市 / 区县 / 51 赛道字典）
server/server.js零依赖中转服务：静态托管 + 认证 + 业务 API + Neon/Supabase/内存三态存储

server/.env.example环境变量模板；真实 .env 与 neon-config.js 已被 .gitignore 排除
vendor/Leaflet / ECharts / SheetJS / leaflet-heat 本地化，规避国内 CDN 不稳定
docs/交接文档（本文件）

API 清单与权限

接口方法权限说明
/api/healthGET公开健康检查 + 存储类型，前端据此切换在线/模拟模式
/api/auth/register / loginPOST公开注册（首用户自动 admin）/ 登录，返回 Bearer Token

认证与权限模型

  • 密码：scrypt + 随机盐 哈希存储；会话为服务端内存 Token（crypto.randomBytes）。
  • 角色：管理员（探迹挖掘 / Excel 导出 / 删除客户 / 用户管理）；普通用户（查看 / 筛选 / 添加客户 / 路线 / 价值分析）。前端隐藏 + 后端 401/403 双重拦截。

Neon 连接协议（零依赖关键）

POST https://<连接串host>/sql
Headers: Neon-Connection-String: <完整连接串>
Body:    { "query": "SELECT …", "params": [ … ] }
Return:  { rows, rowCount, command }

存储优先级：SUPABASE_URL+ANON_KEY（平台注入）→ DATABASE_URL → neon-config.js → 内存。启动时 ensureSchema() 幂等建表。

部署方式

  • 自托管（推荐，真实模式）：任意 Node ≥18 主机，node server.js（零依赖无需 npm install），前端 relayUrl 指向该地址或整目录托管。
  • GitHub Pages：静态托管，git push 自动构建；无后端时为模拟模式。
  • QW Pages：静态镜像；动态+平台数据库需订阅支持（当前订阅不含 Pages 数据库功能）。

网络与运维坑位

  • Clash Verge TUN 模式将流量路由虚拟 IP，阻断 Neon / Supabase 等海外端点（ECONNRESET / 超时）；需对 *.neon.tech、*.supabase.co 加 DIRECT 或换节点。
  • 国内 jsdelivr 不可达、cdnjs 大文件易截断；前端库一律 vendor，下载源用 npmmirror，下载后必须校验文件完整性。

05项目开发约束规范

  1. 密钥后端唯一：探迹 / 天眼查 / 爱企查的 API 密钥、令牌仅存放后端环境变量（.env），禁止暴露前端、禁止存入数据库、禁止提交 git。
  2. 第三方请求后端代理：所有第三方网络请求必须经 server/ 中转，禁止前端直接发起；前端只持有 relayUrl 一个地址。
  3. 坐标强制落库：所有客户必须解析经纬度并入库，保障点位点亮与足迹串联；缺失坐标的客户在列表标红提示。
  4. 双重必填校验：客户名称 / 公司地址 / 法人联系人 / 法人电话，前端与后端同时校验，任一侧不得放宽。
  5. 命名与枚举冻结：客户录入功能统一命名"添加客户"；建联情况仅 已建联/未建联；是否重点/是否注册仅 是/否。
  6. 零依赖约束：后端仅用 Node 内置模块；前端库全部 vendor；新增依赖需评估国内可达性并本地化。
  7. 权限变更管控：角色调整 / 用户删除仅管理员可操作且不可作用于自身；接口层 401/403 强制拦截。
  8. 发布流程：改动经 git push 触发 GitHub Pages 自动构建；密钥文件已在 .gitignore，提交前检查 git status。
